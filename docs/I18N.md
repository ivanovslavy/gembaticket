# GembaTicket — languages (EN / BG / ES)

Added 2026-10-30 (т.10). Before that the whole product was English-only.

## The mechanism

Each app has a small store, `src/i18n.jsx` (the storefront, the dashboard and the scanner each have
their own copy of the same 60 lines):

* `LANGS = ["en", "bg", "es"]` — the one list every switch renders from;
* the active choice lives in `localStorage` under **`gt-lang`**, shared by all three apps, so a buyer
  who switches the storefront to Spanish gets a Spanish ticket page, and an organizer who switches
  the dashboard sees Spanish in the scanner too;
* `detectLang()` honours a saved choice, else the browser's language, else English;
* `document.documentElement.lang` follows the choice.

A page keeps its strings next to the markup that uses them and reads them with `useStr`:

```jsx
const STR = {
  en: { title: "Scanners", rows: (n) => `${n} rows` },
  bg: { title: "Скенери", rows: (n) => `${n} реда` },
  es: { title: "Escáneres", rows: (n) => `${n} filas` },
};

export default function Page() {
  const L = useStr(STR);        // FIRST line of the component
  return <h1>{L.title}</h1>;
}
```

🔑 **The handle is `L`, never `t`.** `const t = useStr(STR)` reads nicely until a `.map((t) => …)`
shadows it — and then `t.title` inside that callback is the row, not the table, and the label
silently renders as `undefined`. Three files in this codebase use `t` as a callback parameter; `L`
collides with nothing.

Values that interpolate something are arrow functions, so a translator can move the placeholder
where the language needs it: `rows: (n) => …` is called as `L.rows(n)`.

The switch sits on every entry surface: the storefront nav (desktop and mobile), the dashboard
topbar **and** its sign-in/sign-up pages (which live outside the layout), the scanner status bar and
its login screen.

## The e-mails

Ten senders, 72 string keys, one `STR` table in `emailService.js` whose three halves carry identical
keys (asserted by the test). The language is **not guessed per message** — it is remembered:

| where | column | set when |
|---|---|---|
| organizer | `Organizer.locale` (default `en`) | registration |
| buyer | `Ticket.buyerLocale` | purchase |

Both come from the `X-Gemba-Lang` header the three apps now send on every call (`reqLocale(req)` in
`src/utils/locale.js`, falling back to `Accept-Language`, then English). So a cancellation e-mail
three months after the purchase is still written in the language that person was reading.

The contact form and the admin security notice stay English on purpose: they are addressed to us.

## How the translations were produced

Not by hand, and not file by file through a chat: the strings went through the **Claude Message
Batches API** (half price, and this work is not interactive). The pipeline lives on the laptop in
`~/Documents/Claude/GembaTicket-scripts/`:

| script | what it does |
|---|---|
| `i18n-batch.py <app> submit\|retry\|blocks` | builds one batch per app, waits, prints token usage and cost |
| `i18n-apply.py` | applies the result — **strictly** (see below) |

The model never rewrites a file. It returns the `{ en, bg, es }` table plus a list of **exact source
snippets to replace**, and the applier

1. refuses any snippet that is not found **exactly once** (a translation job may not half-change a
   40 kB page),
2. rewrites the handle to `L`,
3. inserts the table after the imports,
4. then verifies that **every `api()` call string and the whole hook sequence are unchanged** and
   that every `L.<key>` the file now uses exists in the table — otherwise the file is skipped whole.

Three large pages (`CreateEvent`, `Settings`, `EventScanners`) kept coming back as truncated JSON, so
they went through a block format (`=== TABLE` / `=== EDIT` / `--- FROM` / `--- TO`) with no escaping
at all.

**Cost, 2026-10-30:** 50 frontend files + the e-mail service + the legal drafts =
**$8.70** with the Batch discount (model `claude-sonnet-5`).

## Tests

* `tests/e2e/mail-i18n-e2e.js` — stubs nodemailer before the service loads, renders all ten e-mails
  in all three languages, and asserts three different subjects, nothing `undefined`, no unrendered
  `${…}`, and identical key sets. **100/100**; with the locale ignored in a copy of the service,
  8 assertions go red.
* `tests/e2e/lang-browser-check.js` — a real Chromium over seven screens × three languages: it
  compares the rendered **body** text (several pages are headed by the brand name, which is never
  translated) and checks the switch is on the page. **21/21 rendered, 0 errors, 7/7 different.**

## The three legal pages — translated and live (2026-10-31)

Terms, Privacy and Refund **are** translated and shipping. Each page is one
`CONTENT = { en, bg, es }` table rendered by `LegalPage.jsx` → `LegalBody`, so the structure
(section numbers, subheadings, bullets, callouts) is shared and only the words differ — a
translation cannot quietly drop a clause. The only inline markup inside the legal text is
`**bold**`, `*italic*` and `[text](url)`.

They were generated from the English JSX plus the approved translations in
`~/Documents/Claude/GembaTicket-translations/` by the one-off `ops/legal-i18n/build.py` (private
repo), which refuses to emit anything unless every unit of every language lines up one-to-one.
The generated tables are now the source of truth; `build.py` re-extracts the English from the JSX,
so if you edit a page, add the matching BG/ES lines to the translation markdown or the next run
will fail the line-up check (loudly, by design).

Checked on every edit: the three languages must agree in **block structure**, in **link count**
and in **emphasis count** — a BG or ES page silently losing a clickable complaints-body link or a
bolded legal carve-out is the failure mode this invariant exists to catch.

## What is NOT translated

* `StatusPages.jsx` — **no longer true, it is translated**: it carries a full `STR = { en, bg, es }`
  table with three `useStr` call sites. Only the platform-admin app remains untranslated, and that
  is ours, not a customer surface.

## Still outstanding — `hreflang`

`hreflang` link elements are **still not present**, and they cannot be added meaningfully as the
storefront is currently routed. `hreflang` annotates *alternate URLs*, but language here is not in
the URL at all: `i18n.jsx` keeps the active language in `localStorage` under `gt-lang` (seeded from
`navigator.language`), and the router exposes exactly one path per legal page — `/terms`, `/privacy`,
`/refund`. All three languages render at the same URL.

Emitting three `hreflang` links that all point at one URL would tell a crawler something untrue, so
it has deliberately **not** been done. Adding real `hreflang` requires giving each language its own
addressable URL (a `/bg/...` / `/es/...` prefix, or a `?lang=` the server and router both honour)
plus a canonical per language — a routing change, not a metadata change.
